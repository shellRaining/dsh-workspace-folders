# 工作区文件夹 fork 规划

状态：已确认（2026-11-12），按本文实现。本文写功能规则、接入方式和维护流程，代码层面的约束见同目录上一级的 [AGENTS.md](../AGENTS.md)。调研基于 DSH 0.2.2-rc.1 的发布包和上游源码（截至 0.2.2-rc.2），首个版本对应 DSH 0.2.2-rc.2。

用语：

- 官方包：DSH 自带的工作区包 `@deepseek-ai/dsh-client-ui-workspace`。
- fork：本项目发布的 `@shellraining/dsh-workspace-folders`，显示名"工作区文件夹"。
- 对话：即宿主界面里的"会话"。

## 1. 目标

在左侧侧栏的工作区里加一层文件夹：用户在某个工作区下新建文件夹，把该工作区的对话放进去，文件夹可以折叠。文件夹只改变侧栏的显示方式，不改对话的工作目录、历史记录和所属工作区。

fork 复制官方包，在原有的工作区列表里加上文件夹，再替换掉官方包，侧栏只有一个视图。官方已有的搜索、视图选项、拖拽排序、工作区菜单，以及其他插件挂在对话行上的标记和菜单项全部保留。没有建文件夹时，fork 的外观和行为与官方包一致。

视觉只用 DSH 的设计 token，装了 fluent theme 后自动获得与官方行相同的亚克力、Reveal 和按压效果。

## 2. 功能

### 文件夹

- 每个工作区可以有若干文件夹，只有一层。宿主的"未分组"（不属于任何工作区的对话）下不能建文件夹。
- 新建有两个入口：工作区菜单里的"新建文件夹"，以及对话菜单里的"移动到文件夹 ▸ 新建文件夹…"，后者一步完成新建和移入。宿主界面里的"文件夹"通常指磁盘目录，所以新建对话框注明"只用于整理侧栏，不会在磁盘上创建目录"。
- 文件夹菜单提供重命名和删除。删除前确认，里面的对话回到文件夹外，不删除也不归档任何对话。
- 文件夹的折叠状态在本浏览器记住。

### 对话归属

- 一个对话最多属于一个文件夹，只能进入所属工作区的文件夹。
- 对话菜单的"移动到文件夹"列出该工作区的文件夹，另有"移出文件夹"。

### 拖拽

- 拖到文件夹行上：移入该文件夹，只改归属，不切换排序方式。"手动排序"时排在文件夹最前，免得被收进"展开其余"。折叠的文件夹也能放入，放入后不自动展开。
- 拖到所属工作区的行上：移出文件夹，同样只改归属。"手动排序"时排在文件夹外的对话最前。
- 拖到两行之间：落点在文件夹内就移入，在文件夹外就移出，并放在该位置。这和官方的拖动排序一样，"最近更新"时会切换成"手动排序"。
- 沿用官方的限制：对话不能拖到其他工作区。文件夹本身不能拖动。单列表和搜索结果里的拖拽保持官方行为。

### 显示规则

- 分组方式："按工作区"和"按工作区树"显示文件夹，工作区树里的顺序是子工作区、文件夹、文件夹外的对话。"单列表"不显示文件夹，按官方方式平铺，归属保留。
- 排序：文件夹之间按名称排序。文件夹内置顶的对话排在最前，其余跟随当前的排序方式，"手动排序"时沿用该工作区的手动顺序。
- 筛选：已归档的对话按当前筛选显示或隐藏，归属一直保留，取消归档后回到原文件夹。"仅显示已归档"时隐藏没有已归档对话的文件夹，其他筛选下空文件夹照常显示。
- 搜索：结果沿用官方的平铺列表，不显示文件夹。
- "展开其余"：文件夹行总是显示，不占工作区"前 5 条"的名额。展开的文件夹内同样先显示前 5 条，其余收进"展开其余"。
- 当前对话所在的文件夹，文件夹图标高亮，与官方工作区树里祖先工作区的高亮一致。
- 分叉出的新对话不继承文件夹，出现在文件夹外，与官方不继承置顶的做法一致。
- 宿主目前没有删除对话的入口。归属只在对话出现在列表里时生效，列表里找不到的对话不显示，也不影响文件夹。
- 从列表移除工作区时保留它的文件夹。宿主重新添加同一目录时会分配新的工作区 ID，所以文件夹按工作区的目录记录，重新添加后文件夹和归属恢复。

### 不做

多层嵌套（暂不做），一个对话属于多个文件夹或标签，文件夹级的指令、模型和知识库，用户自选的文件夹颜色、图标和 emoji，AI 自动归类，批量多选，未读计数，跨工作区的文件夹，文件夹的手动排序和拖动，"未分组"下的文件夹，单列表和搜索结果里的文件夹，多个窗口之间的实时同步，改动官方已有的行为或修复上游问题。

在文件夹里直接新建对话，放到 MVP 之后按需做。

## 3. 数据

- 文件夹数据存在宿主端，用 DSH 的存储服务，文件是 `~/.dsh/storages/workspace_folders.json`，可以备份。同一 DSH 宿主的所有客户端共享，桌面端和浏览器看到的是同一份。
- 只存两类数据：每个工作区的文件夹列表，以及对话到文件夹的归属。折叠状态属于浏览状态，存在浏览器本地。
- 新建、重命名、删除、移动都按单个操作写入宿主，几个窗口同时操作不会整份互相覆盖。不做实时推送，其他窗口刷新后看到最新结果。
- 卸载 fork 不删除数据，重新安装后恢复。
- 读写文件夹数据的代码放在 fork 的宿主端，以 Typert Remote `workspaceFolders` 提供给浏览器，鉴权和参数校验走宿主的 Gateway。官方包的宿主端是空函数，新增代码不会和上游冲突。
- 官方的视图存储（分组方式、排序方式、手动顺序、展开状态、当前对话）照常使用，文件夹数据不写进去。这样在官方包和 fork 之间切换时，两边的设置都不丢。

## 4. 视觉与主题适配

- 文件夹行复用官方工作区行和对话行的组件和样式，高度、悬停、选中和焦点框都与官方行一致；回车和空格展开或折叠文件夹（官方工作区行没有键盘展开，这里补上）。新增样式只引用 DSH 设计 token 和侧栏的布局变量，不写死颜色和圆角。
- 文件夹图标与工作区相同，开合两种状态各用对应的图标，靠缩进和工作区区分。悬停时图标换成折叠箭头，与工作区行一致。
- 文件夹行比所属工作区缩进一级，文件夹里的对话与文件夹行对齐，和官方工作区树里子工作区的对话一样。不显示对话数量，官方行也不显示。
- 拖到文件夹行或工作区行上时，该行高亮，表示松手后会移入或移出；两行之间的落点提示沿用官方拖动排序的样式。
- 对话框、菜单和输入框沿用官方重命名、删除工作区时用的组件。
- 行的语义与官方一致，fluent theme 的 Reveal、按压动效和焦点框直接作用到文件夹行。fluent theme 只需要识别 fork 的包名，见第 8 节。
- 减少动态效果、无悬停设备上常显操作按钮，都沿用官方的处理。

完整的页面检查组合：明暗主题、fluent theme 开和关、减少动态效果；窄屏抽屉和侧栏收起；三种分组方式和三种筛选；两种排序方式下的拖入和拖出。

## 5. 接入方式

fork 安装后，它自带的 bundle patch 停用官方包，并在同一位置插入 fork；卸载或停用 fork，官方包随之恢复。以下是源码核对的结论，第一个里程碑会在实际页面验证：

- 客户端只加载已启用的插件。另有 13 个宿主包在 manifest 的 `dsh.client.inject` 里声明了官方包，这个声明只用来排加载顺序，找不到这个包时直接跳过，所以停用后不会被重新拉起。
- 没有宿主包在运行时按包名引用官方包，它们都通过 `uiWorkspace` 等服务和 slot 交互。fork 保留服务名和 slot 名，侧栏、定时任务、"在本机显示"等功能照常工作。
- DSH 启动时，`engines.dsh` 不满足的 bundle 会连同它的 patch 一起跳过。fork 与当前 DSH 版本不匹配时，停用不会生效，侧栏回到官方视图。
- 宿主注入的 CSS module 样式标签以包名为键。改名后，按官方包名查找宿主类名的插件会落空。fluent theme 就是一个，它只查了搜索结果行。
- 替换 `sidebar.workspaces` 的插件（如 dsh-better-workspace）照样能盖住 fork，和盖住官方包一样；只给对话行加标记的插件不受影响。

## 6. 仓库

- 在 GitHub 上 fork `deepseek-ai/deepseek-harness`（MIT，约 360MB），仓库改名为 `dsh-workspace-folders`。公开仓库的 fork 必须公开。保留上游许可证和署名。
- 默认分支设为 `main`，内容是上游 master 加文件夹功能。fork 自带的 master 只作上游镜像，不往上面提交。
- 上游自带的工作流在 GitHub 设置里停用，不改它们的文件。本仓库的流水线放在新文件里。
- 维护规则写在 `packages/client/ui-workspace/AGENTS.md`。上游这个目录没有该文件，不会冲突；根目录的 AGENTS.md 属于上游，不改。
- 不新增测试。上游这个包自带的测试原样保留，作为合并检查的一部分。

### 改动边界

目标是每次合并上游时，冲突只出在少数位置。

1. 包清单保持上游的包名和版本号，只加 Typert 要求的导出和 `files` 条目。发布用的包名、版本、`engines.dsh`、README、bundle patch、图标都在新目录 `fork/` 里，由 `fork/build.ts` 在构建时套上。改名不放在 `main` 的包清单里，是因为另有 15 个上游包以 `workspace:*` 按包名依赖这个包，改名会让整个仓库装不上依赖。
2. 文件夹功能写在新文件里，上游文件只加必要的接入点，不改依赖和 `pnpm-lock.yaml`。
3. 不格式化、不重命名、不顺手修上游代码，上游的问题留给上游。
4. 没有文件夹数据时，行为与官方包一致，上游测试不改动且全部通过。我们的改动让上游测试失败时，改我们的代码，不改测试。

2026-10-10 到 11-04，上游 master 有 108 次提交改到这个包，改得最多的源码文件是 `Rows.tsx`（23 次）、`WorkspaceBrowser.tsx` 和客户端 `index.ts`（各 16 次）、`slots.ts`（13 次）、`navigation.ts`（10 次）。文件夹和拖拽的接入点落在 `WorkspaceBrowser.tsx`、`Rows.tsx`、客户端 `index.ts` 和 `slots.ts`，每处只有几行，冲突时按 AGENTS.md 放回。README 不改，包清单只加行，这两处基本不会冲突。

## 7. 同步与发布

`main` 逐个提交跟踪上游 master，发布则对齐 DSH 的 release tag。两条线分开的原因：fork 运行在已安装的 DSH 上，调用的是该版本的其他宿主包，master 的最新代码可能依赖还没发布的接口，所以每次发布的内容必须是"某个 release tag 上的官方包加文件夹功能"。

### 主线跟踪

- GitHub Actions 的 `folders-sync` 每天北京时间 03:17 运行一次，也可以手动触发。改到这个包的上游提交逐个合并进 `main`，每合并一个检查一次；没碰这个包的提交成批合并，最后检查一次。检查包括类型检查、fork 构建和这个包的上游测试。
- 合并干净且检查通过，就自动推送到 `main`。遇到冲突或检查失败，就停在那个上游提交，开 issue 写明是哪个提交；人工解决后，任务从那里继续。推送用部署密钥，因为合入的上游提交可能改到工作流文件，`GITHUB_TOKEN` 推不了这类改动。
- 定时任务同时把上游 master 镜像到 fork 的 master，并停用随上游提交新增的工作流。它不改版本号，不发布。
- 公开仓库的 master 是成批更新的：11-10 晚上 master 还停在 11-04 的提交，之后的 106 个合并提交到 11-11 才和 rc.2 一起出现。每批更新一到，定时任务就把其中的提交逐个过一遍。

### 发布

- 上游每打一个 `dsh-v*` tag，定时任务从 tag 切出 `release/<版本>`，把 `main` 相对上游的改动（这个包的目录、根 `tsconfig.host.json` 的一行和两个工作流文件）以三方合并的方式应用上去，检查通过后推送并开 issue，构建产物作为运行产物上传。tag 和 `main` 之间这个包的内容通常一致（rc.2 比切点只多出 7 个发布提交，碰到这个包的只有版本号），所以通常不会冲突；冲突或检查失败时同样开 issue。
- 你的 DSH 升级到这个版本后做页面冒烟检查，范围是文件夹显示、菜单移动、拖入拖出和 fluent theme。检查通过后，在发布分支上改 `fork/manifest.json` 的 `engines.dsh` 和版本号并推送，`folders-release` 流水线发布到 npm。第 4 节的完整组合只在 MVP 和接入点有较大改动时做。
- `engines.dsh` 写死为对应的那一个 DSH 版本，不用版本范围。fork 和侧栏、对话等宿主包按版本耦合，旧代码跑在新宿主上可能出错，而官方包已被停用，出错时没有官方视图可以退回。
- DSH 升级后到 fork 发新版之前，DSH 跳过 fork，侧栏回到官方视图，文件夹数据保留；升级 fork 后恢复。
- fork 的版本号从 0.1.0 起独立递增，README 列出每个版本对应的 DSH 版本。
- 首个版本在本机手动发布，并绑定 npm trusted publishing，之后走流水线。

### 开发环境

- 首次要安装整个上游 monorepo 的依赖（pnpm 11，Node 24.9 以上）。这个包的构建依赖上游的 tsdown 配置、Typert 生成器和 TypeScript 项目引用，测试依赖上游的客户端测试运行时，都只能在完整仓库里跑，CI 每次也要完整安装。
- 当前 DSH 版本的包内容和 `main` 一致时直接在 `main` 上开发，否则在对应的发布分支上开发，这样才能在实际页面检查，完成后合回 `main`。
- 在实际页面验证时，把 profile 里的 fork 链接到仓库外的构建输出目录，会修改 profile 配置，动手前征求你同意。web 和 desktop 两个 profile 各自安装。具体命令见 AGENTS.md。

## 8. dsh-plugins 的改动

- fluent theme：搜索结果行的样式查找同时识别官方包名和 fork 包名，发一个补丁版本。
- 根 README 的插件表加一行，链接到 fork 仓库，注明它替换官方工作区列表、跟随 DSH 版本发布。
- 删除 `plugins/workspace-folders/`。

## 9. 风险

- 合并成本：接入点落在上游改得最勤的文件里，见第 6 节。上游重写工作区浏览器时，接入要整体重做。
- 发布滞后：DSH 升级后，要等页面检查通过才有对应的 fork 版本，这段时间侧栏没有文件夹，数据不丢。DSH 的 alpha 和 rc 间隔只有几天。
- 其他按官方包名定位样式的第三方主题插件，在 fork 下会失去对应样式，只能由它们自行适配。
- npm 包公开后，别人安装也受版本跟随的限制，README 写清兼容版本和失效表现。
- 公开仓库连续 60 天没有活动时，GitHub 会停用定时任务，需要手动重新启用。
- 上游以后自己做了分组功能，fork 就可以退役，数据是否迁移到时再定。

## 10. 里程碑

里程碑 0 到 2 的代码一起完成，页面验证合并成一次，按下面的清单逐项确认。任何一项走不通，fork 路线就要重新评估。

0. 接入：
   - 官方包被停用，fork 正常显示，切换前后视图设置不丢。
   - 其他插件挂在对话行上的标记、菜单项和悬浮卡正常。
   - fluent theme 的效果正常。
   - 卸载 fork 后官方包恢复。
   - `engines.dsh` 不满足时，侧栏回到官方视图。
   - 安装、升级、卸载后是否需要重启 DSH，结果写进 README。
1. 定时同步和发布流水线：手动触发一次 `folders-sync`，确认它能在 CI 里装好依赖、只跑这个包的上游测试，并为当前 tag 准备好发布分支。
2. MVP：第 2 节的功能（含拖入拖出）、宿主端存储、主题适配，以及 fluent theme 的补丁版本。
3. 之后按需：在文件夹里直接新建对话。
